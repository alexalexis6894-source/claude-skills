# Trio: три призмы, один план, доведение до конца

Три агента смотрят на одну задачу разными глазами, их планы сводятся в один,
и он выполняется до зелёного прогона и пуша. Не советы, а сделанная работа.

## Когда звать

| Звать | Не звать |
|---|---|
| Новая фича дороже двух часов | Правка в одну-две строки |
| Рефакторинг, распил больших файлов | Опечатка, переименование |
| Миграция, смена схемы данных | Вопрос «покажи файл» |
| Задача, где непонятно, с чего начать | Задача с очевидным единственным решением |

## Три призмы

Тексты лежат рядом: `.claude/skills/trio/linzy/` (в проекте или в `~/.claude/skills/trio/linzy/`).

| Файл | Кто это | Что ищет |
|---|---|---|
| `inzhener.md` | инженерный менеджер (plan-eng-review, gstack) | объём, радиус поражения, тесты, ASCII-схемы, «скучное по умолчанию» |
| `arhitektor.md` | архитектор глубины (improve-codebase-architecture, mattpocock) | мелкие модули, швы, тест на удаление, что углубить ДО фичи |
| `kachestvo.md` | строгий ревьюер (thermo-nuclear, cursor) | ход код-дзюдо, правило 1000 строк, спагетти-рост, запреты |

Призмы написаны по мотивам открытых скиллов (gstack, mattpocock/skills, ревью-скилл cursor) и сохранили
их английский текст. Ссылки внутри на `/office-hours`, `ExitPlanMode`, `AskUserQuestion`, служебные
блоки телеметрии и «GSTACK REVIEW REPORT» относятся к исходной среде: если их нет, пропускать, берётся
только способ смотреть на задачу.

Призмы намеренно спорят между собой. Инженер режет объём, архитектор
хочет углубить модули до фичи, ревьюер требует сначала разобрать завалы.
Спор и есть ценность: то, на чём они СОШЛИСЬ, почти наверняка правда.

## Порядок

### Шаг 1. Разведка перед брифом (делает ведущий, не агенты)

Агенты прочитают код сами, но брифу нужны числа, которых в коде не видно.
Собрать до запуска:

- Скиллы под задачу: сначала прогнать `skill-scout`, выбранные скиллы вписать
  в бриф путями к `SKILL.md`, чтобы все три агента планировали через них.
- Размеры файлов, которые задача заденет: `wc -l`. Файл за 1000 строк это
  ограничение, а не мелочь.
- Бюджет сборки, если он есть: сколько КБ в запасе и чем сторожится.
- Команда полной проверки и сколько она идёт.
- Что по теме УЖЕ написано. Половина задач оказывается наполовину сделанной,
  и без этого агенты изобретут существующее заново.
- Соглашения репозитория: язык идентификаторов и комментариев, запреты (`CLAUDE.md`, `CONTRIBUTING.md`, если есть).

### Шаг 2. Бриф

Один файл во временной папке (scratchpad или `/tmp`), один и тот же для всех трёх. Обязательно:

1. **Дословная просьба пользователя.** Не пересказ: агент должен видеть,
   что именно человек сказал.
2. **Разбор просьбы** одним абзацем: что это значит на языке кода.
3. **Что уже есть** с именами файлов, функций и типов. Самый важный раздел.
4. **Жёсткие ограничения** таблицей: размеры файлов, бюджет, экран, тесты.
5. **Вопросы, на которые обязан ответить план**, списком.
6. Строка «другие два агента смотрят на ту же задачу другими глазами».

### Шаг 3. Три агента параллельно

Все три в ОДНОМ сообщении, иначе они пойдут по очереди.

Каждому:
- прочитать свою призму из `linzy/<файл>.md` этого скилла и бриф;
- прочитать названные в брифе файлы кода;
- **править файлы ЗАПРЕЩЕНО**, только чтение и план;
- не выполнять служебные bash-блоки из текста призмы (телеметрия, кэши,
  вопросы пользователю): они не для субагента;
- отвечать по-русски, структурой из брифа, с именами файлов и типами.

### Шаг 4. Сведение

Не склейка, а решение. Свести таблицей:

| Правило сведения | Как применять |
|---|---|
| Сошлись двое из трёх | берём, объяснять не надо |
| Сошлись все трое на баге | это почти наверняка настоящий баг, чинить обязательно |
| Разошлись | выбрать одно, назвать причину выбора одной строкой |
| Один требует подготовки на 8 часов | взять из неё то, что фича трогает, остальное записать на потом |
| Кто-то предложил новую библиотеку | проверить по бюджету и по «скучному по умолчанию» |

Сведение показать пользователю ДО реализации, коротко: таблица «вопрос,
что решили агенты, что взял». Три-пять строк, не пересказ планов.

### Шаг 5. Выполнение

Дальше обычная работа, но с двумя правилами:

- **Порядок из плана соблюдать.** Развязка идёт до фичи, а не «потом».
  Отдельными коммитами, чтобы откатывалось по одному.
- **Запреты из призмы качества это запреты.** Если план сказал «никакого
  SVG», не появляться SVG.

### Шаг 6. Закрытие

Полный прогон, зелёный. Коммит с объяснением ПОЧЕМУ, а не что. Пуш, если так принято в проекте (ветка и порядок слияния по правилам репозитория).
Живая проверка результата глазами, если это экран.

## Грабли, на которые уже наступали

| Грабля | Что делать |
|---|---|
| **Кириллица в ключах JSON-схемы** роняет всех агентов разом: `400 input_schema.properties should match ^[a-zA-Z0-9_.-]$` | имена полей схемы латиницей, значения по-русски |
| Сводящий агент получил пустые находки и **сочинил сводку по памяти** | в промпт сведения: «пришло пусто, значит так и напиши ПУСТО и не сочиняй» |
| `npx prettier` без конфига в репозитории **переформатировал файлы целиком** | не гонять форматтер, которого нет в зависимостях |
| Тесты считали количество кнопок: `toBe(5)` | искать в тестах числа, завязанные на то, что меняешь |
| Тугой цикл `curl` по проду **включил защиту Vercel от ботов**, 403 | ждать деплой с паузами, а не в цикле |
| Правило CSS не применилось: media-блок стоял ВЫШЕ базового правила | при равной специфичности побеждает последнее по файлу |
| Агенты полезли выполнять bash из текста призмы | прямо запретить в промпте |

## Что этот стек даёт сверх одного плана

- **Распил больших файлов** предлагает призма качества, и она же называет
  конкретные строки. Один агент до этого обычно не доходит: он занят фичей.
- **Дыры в существующем коде** находит призма архитектора через тест на
  удаление, а не через чтение подряд.
- **Объём режет** призма инженера, и это единственная, кто задаёт вопрос
  «а что из этого НЕ делать в первой версии».

## Чего этот стек не заменяет

Разговор с пользователем о том, ЧТО делать. Три плана отвечают на «как»,
и если задача поставлена расплывчато, все три будут расплывчатыми.
Непонятна задача, значит сначала один короткий вопрос, потом trio.
